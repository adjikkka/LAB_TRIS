# Техническое задание на ЛР1

## 1. Предметная область
Заказчик: Комендант общежития.
Процесс: Обработка заявок жильцов на устранение бытовых неполадок (протечки, проблемы с электрикой, мебелью).

## 2. Как есть (проблемы)
Сейчас жильцы сообщают о проблемах устно или по телефону. Комендант записывает их в бумажный журнал. Информация теряется, если комендант заболел или ушёл в отпуск. Жильцы не знают, когда придёт мастер. Мастера не видят список своих задач в одном месте. Нет статистики по частым поломкам. Невозможно доказать, что работа была выполнена. Нет чёткого разделения, кто за что отвечает. Бумажный журнал легко потерять. При передаче смены информация искажается.

## 3. Как будет (одна запись)
В системе создаётся электронная запись «Обращение». Она содержит: уникальный номер (например, ОБР-001), заголовок (например, «Протечка крана»), ссылку на комнату (roomId), текстовое описание, статус (New, InProgress, Closed, Cancelled), дату создания и назначенного исполнителя.

## 4. Граница системы
**Внутри семестра:** Создание обращения, назначение исполнителя, смена статуса, просмотр списка обращений.
**Снаружи:** Бухгалтерия, склад запчастей, мобильное приложение, SMS-уведомления.

## 5. Роли

| Роль | Создать | Назначить | Сменить статус | Смотреть все |
| :--- | :---: | :---: | :---: | :---: |
| Комендант | Да | Да | Нет | Да |
| Сантехник | Нет | Нет | Да (свои) | Нет |
| Электрик | Нет | Нет | Да (свои) | Нет |

## 6. Функциональные требования
1.  Комендант может создать обращение, указав заголовок, комнату и описание.
2.  Комендант видит список всех обращений с фильтром по статусу.
3.  Комендант может назначить исполнителя на обращение в статусе New.
4.  Исполнитель видит только те обращения, которые назначены на него.
5.  Исполнитель может перевести своё обращение из New в InProgress.
6.  Исполнитель может перевести своё обращение из InProgress в Closed.
7.  Комендант может отменить обращение (статус Cancelled).
8.  Система автоматически присваивает человеческий номер при создании.
9.  Система запрещает менять статус чужого обращения.
10. Система запрещает создавать обращение с пустым описанием.

## 7. Нефункциональные требования
1.  Данные сохраняются в PostgreSQL и не исчезают после перезапуска сервера.
2.  Время отклика API не более 1 секунды.
3.  Пароли пользователей хранятся в хешированном виде.
4.  Интерфейс должен корректно отображаться в браузере Chrome.

## 8. Use Case: Создание обращения
**Актёр:** Комендант.
**Предусловие:** Комендант авторизован в системе.
**Основной поток:**
1.  Комендант нажимает «Создать обращение».
2.  Система показывает форму.
3.  Комендант вводит заголовок, выбирает комнату из справочника, пишет описание.
4.  Комендант нажимает «Сохранить».
5.  Система проверяет данные, создаёт запись со статусом New и присваивает номер.
6.  Система показывает сообщение об успехе и перенаправляет в список.
**Альтернатива:** Если поле «Описание» пустое, система показывает ошибку и не сохраняет.
**Постусловие:** В БД появилась новая запись со статусом New.

## 9. Три критерия (Given-When-Then)

**1. Создать**
- **Дано:** Комендант вошёл в систему.
- **Когда:** Заполняет заголовок (5-80 символов), выбирает комнату, пишет описание (10-500 символов), жмёт «Создать».
- **Тогда:** Создана запись со статусом New и номером.

**2. Назначить**
- **Дано:** Комендант и обращение в статусе New.
- **Когда:** Комендант назначает исполнителя отдельным действием.
- **Тогда:** Исполнитель записан в обращение. Статус не меняется.

**3. В работу**
- **Дано:** Сантехник вошёл в систему, ему назначено обращение в статусе New.
- **Когда:** Сантехник переводит обращение в InProgress.
- **Тогда:** Статус меняется на InProgress. Другой сантехник не может изменить это обращение.
