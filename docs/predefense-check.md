## 2. Запрет новых больших функций

Не добавлять: чат, карту, мобильное приложение, редизайн, вторую
авторизацию, аналитику, смену стека. Допустима одна согласованная мелкая
доработка после основных критериев.

## 3. Приоритет дефектов (исправлять сверху вниз)

1. Стенд не запускается по README.
2. Не выполняется создание, назначение или `InProgress`.
3. Нет сохранения после рестарта.
4. Ошибочный код: 500 вместо 400/404/409.
5. Нарушение доступа: нет 401/403.
6. Ошибка документации.
7. Косметика.

После каждого исправления — повторный прогон затронутого критерия целиком.

## 4. План демо на 7 минут

### 0:00–0:30 — контекст
- Заказчик: комендант общежития.
- Главный объект: обращение жильца (`Ticket`), номер `ОБР-2026-NNN`.
- Сценарий: создать → назначить → в работу, затем 401/403 и рестарт.

### 0:30–4:30 — основной путь
1. Войти комендантом (`komendant`).
2. Создать обращение через UI (`/new`).
3. Показать 201 и `id` в Network.
4. Показать тот же `id` в SQL (`SELECT … WHERE id = …`).
5. Назначить исполнителя (сантехник).
6. Войти исполнителем (`santehnik`).
7. Перевести то же обращение в `InProgress`.

### 4:30–6:30 — защита и сохранность
1. `POST /api/tickets` без входа → 401.
2. Чужая запись исполнителем → 403.
3. Перезапустить API (`Ctrl+C`, `dotnet run`).
4. Показать, что запись сохранилась.

### 6:30–7:00 — завершение
- Назвать один известный предел (например, генерация номера без защиты
  от гонки — `docs/known-defects.md`).
- Остановиться и принять вопросы.

Стенд разворачивается **до** начала демо: не начинать с установки Node.

## 5. Повтор трёх критериев после исправлений (один новый id)

| Критерий | Дано | Когда | Тогда | Факт |
|---|---|---|---|---|
| создать | комендант вошёл | заполнил форму (тема 5–80, комната, описание 10–500) | POST 201, статус `New` | |
| назначить | запись `New` | выбрал исполнителя | assignee сохранён, статус не изменился | |
| в работу | вошёл назначенный | выбрал `InProgress` | статус изменён | |

Для каждого критерия указать: экран, запрос Network, строку PostgreSQL
и результат после рестарта.

## 6. Вопросы, которые зададут на защите

Ответить своими словами, затем показать файл или экран:

- Чем информационная система не сайт кафедры? — есть процесс со сменой
  состояния (статусы обращения) и роли с разными правами.
- Почему браузер не подключается к PostgreSQL сам? — только сервер
  (`backend`) читает базу; клиент ходит в API (`docs/api-contract.md`).
- Зачем два разных PATCH, а не одна «сохранить заявку»? — назначение и
  смена статуса — разные действия с разными правами (ТЗ ЛР1, критерии 2 и 3).
- Почему название комнаты не пишут в каждом обращении? — 3НФ: имя хранится
  в `rooms`, в обращении внешний ключ `room_id` (`docs/data-model.md`).
- Почему пароль не кодируют Base64? — Base64 легко обратить; нужен
  хэш с солью (`PasswordHasher`, ЛР11).
- Что сознательно не сделали и зачем? — `docs/known-defects.md` (A-01…A-07)
  и запас под ВКР (`docs/project-proposal.md`, раздел 7).
