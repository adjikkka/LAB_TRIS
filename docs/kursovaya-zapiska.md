## 1. Анализ и требования

Заказчик — комендант студенческого общежития КГЭУ. Жильцы сообщают о
бытовых неполадках (протечки, электрика, мебель) устно или по телефону;
комендант ведёт бумажный журнал. Информация теряется при передаче смены,
жильцы не знают, когда придёт мастер, мастера не видят своих задач, нет
статистики по частым поломкам, невозможно доказать выполнение работы.
Процесс со сменой состояния («обращение» от `New` до `Closed` /
`Cancelled`) и две роли с разными правами (комендант и исполнители)
оправдывают создание информационной системы.

Роли: **Комендант** — создаёт и назначает, видит все, отменяет;
**Сантехник / Электрик** — ведут статус только назначенных им обращений.
Граница семестра (MVP): создание, назначение, смена статуса, просмотр
списка с фильтром. Вне границы: оплата, склад, мобильное приложение,
SMS, интеграции.

Три обязательных критерия приёмки (дано / когда / тогда) —
в `docs/lab-01-requirements.md`, раздел 9: создать (POST 201, статус
`New`, номер), назначить (assignee записан, статус не меняется),
в работу (`New → InProgress`, чужой исполнитель не может).

**Артефакты:** `docs/lab-01-requirements.md`, `docs/project-proposal.md`,
`docs/requirements-matrix.md`.

## 2. Проектирование и архитектура

Три узла: клиент Vue 3 + Vite (`localhost:5173`) → сервер ASP.NET Core
(`localhost:5000`) → PostgreSQL (`localhost:5432`). Клиент не обращается
к базе напрямую — все операции через API (это архитектура web-ИС семестра).

Модель данных: главная сущность `Ticket` (обращение: id, number, title,
description, status, roomId, createdByUserId, assigneeUserId), справочник
`Room` (комнаты), пользователь `User`. Четыре статуса: `New`,
`InProgress`, `Closed`, `Cancelled`. Назначение исполнителя и смена
статуса — разные действия. Проверка 3НФ: название комнаты хранится один
раз в `Room`, в обращении — внешний ключ `roomId`.

Черновик REST из ЛР2: `POST /api/tickets`, `GET /api/tickets`,
`GET /api/tickets/{id}`, `PATCH /api/tickets/{id}/assignee`,
`PATCH /api/tickets/{id}/status`.

**Артефакты:** `docs/architecture.md`, `docs/data-model.md`,
`docs/api-contract.md`.

## 3. Клиентская часть (UI)

Стек: Vue 3 + Vite, JavaScript (не TypeScript), vue-router. Три экрана:
список `/` (таблица с номером, темой, комнатой, статусом, исполнителем),
создание `/new`, вход `/login`; шапка с меню — компонент `AppHeader`
вне `router-view`.

Таблица получает массив через props (`TicketTable`), единый источник —
`src/ticketsStore.js`. Клиентская проверка полей: тема 5–80 после `trim`,
комната — целое больше нуля (`v-model.number`), описание 10–500;
отправка через `@submit.prevent`, защита от двойного клика
(`isSubmitting`, `disabled`, текст «Создаём…»).

Список различает четыре состояния: загрузка / пусто (`200` и `[]`) /
данные / ошибка; тексты отказов различаются: «проверьте поля» (400),
«сервер не смог обработать запрос» (500), «нет связи» (ответа нет).
Семантика: `main`, `form`, `label` у каждого поля, `table`,
`:key` в `v-for`, `autofocus`. Пользовательский текст выводится
интерполяцией `{{ }}`, `v-html` не используется.

**Артефакты:** `frontend/src/`, отчёты `docs/reports/lab-03.md` —
`lab-06.md`, экраны и Network в скринах отчётов.

## 4. Сервер и программный интерфейс (API)

Каркас ЛР7: порт 5000, Swagger в Development, служебные `/health`
(только liveness) и `/info`; контроллер тонкий, правила — в сервисе,
сервис внедрён через DI (`ITicketService`).

REST ЛР8: `POST` создаёт запись (201: сервер задаёт `id`, номер
`ОБР-2026-NNN`, статус `New`, пустого исполнителя), `GET` списка
(пустой список — `200 []`), `GET` по id (`404` при отсутствии),
два отдельных `PATCH` — назначение и статус. Коды отказов: 400 —
валидация полей (тема 5–80, описание 10–500, комната существует),
404 — нет записи, 409 — нарушение правила процесса («в работу без
исполнителя», запрещённый переход, повторное назначение), 500 —
неожиданный сбой: в лог одна строка с типом ошибки, клиенту безопасный
`ProblemDetails` без стека.

Вход ЛР11: `POST /api/auth/login` возвращает учебный JWT; `401` — гость,
`403` — роль не та или чужая запись.

**Артефакты:** `backend/Controllers/`, `backend/Dtos/`,
`backend/Services/TicketService.cs`, коллекция
`docs/api-collection/tickets.postman_collection.json`.

## 5. База данных

PostgreSQL. SQL-схема ЛР9 (`db/schema.sql`): таблицы `rooms`, `users`,
`tickets`; внешние ключи `room_id`, `created_by_user_id`,
`assignee_user_id` (`ON DELETE RESTRICT`); `CHECK` статуса на четыре
значения; уникальный номер; индексы по статусу, комнате и исполнителю
с комментариями «зачем». Запросы: фильтр+сортировка, JOIN с названием
комнаты, GROUP BY по статусам (все четыре группы), загрузка исполнителей.

EF Core ЛР10: `AppDbContext` с явными именами таблиц и столбцов
(совпадают со схемой ЛР9 — таблица соответствия в
`docs/reports/lab-10.md`), миграция `InitialCreate` в Git, строка
подключения через user-secrets (пароля в репозитории нет).
Доказательство — рестарт-тест: запись существует после перезапуска API.

**Артефакты:** `db/`, `backend/Data/AppDbContext.cs`,
`backend/Migrations/`, отчёты `docs/reports/lab-09.md`, `lab-10.md`.

## 6. Безопасность и тестирование

Аутентификация и авторизация различены: `401` — личность не установлена,
`403` — действие не твоё. Способ входа один — JWT в заголовке
`Authorization`. Пароли — хэш PBKDF2 (`PasswordHasher` ASP.NET Identity):
в таблице `password_hash`, не открытый текст и не Base64. Проверка
владения — в сервисе: исполнитель меняет статус только записи со своим
`assigneeUserId`; комендант не меняет рабочий статус. Матрица «роль ×
действие» — `docs/role-matrix.md`.

XSS: пользовательский текст не выводится как HTML (`{{ description }}`),
`<script>` в описании показывается текстом. SQL-инъекции: запросы через
EF Core с параметрами, конкатенации нет. Позитив и негатив по трём
критериям ЛР1 повторяются на развёрнутом стенде
(`docs/acceptance-check.md`, `docs/predefense-check.md`).

**Артефакты:** `docs/role-matrix.md`, `backend/Auth/JwtTokenService.cs`,
скрины 401/403 в `docs/reports/lab-11.md`.

смена статуса, список с фильтром по роли, вход, сохранность данных.
Известные ограничения зафиксированы честно (`docs/known-defects.md`);
запас под ВКР — `docs/project-proposal.md`, раздел 7.

**Артефакты:** корневой `README.md`, `docs/predefense-check.md`,
