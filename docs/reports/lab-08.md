## 1. Цель

REST главного объекта: создать, прочитать, отдельно назначить исполнителя,
отдельно сменить статус. Предсказуемые ответы `201 / 400 / 404 / 409`.
Ошибки логируются на сервере без stack trace клиенту.

## 2. Что сделали

1. Сверили имена ресурса и полей с ЛР2: ресурс `tickets`, поля
   `title`, `roomId`, `description`, статусы `New`, `InProgress`,
   `Closed`, `Cancelled` (маппинг курса — в `docs/data-model.md`).
2. Создали DTO (`backend/Dtos/`): вход создания `CreateTicketRequest`
   (только поля человека: title, roomId, description — без id и status),
   `AssignTicketRequest`, `UpdateTicketStatusRequest`, ответ `TicketResponse`.
3. `Models/Ticket.cs` — сущность; `Services/TicketService.cs` — правила
   процесса; контроллер тонкий: принял HTTP, вызвал сервис, вернул код.
4. Маршруты (`backend/Controllers/TicketsController.cs`):

   | Метод и путь | Успех | Назначение |
   |---|---:|---|
   | `POST /api/tickets` | 201 | создать запись (id, number, `New` задаёт сервер) |
   | `GET /api/tickets` | 200 | список, включая `[]` |
   | `GET /api/tickets/{id}` | 200 | одна запись |
   | `PATCH /api/tickets/{id}/assignee` | 200 | назначить исполнителя |
   | `PATCH /api/tickets/{id}/status` | 200 | сменить статус |

   `DELETE` не делаем, общий PATCH «изменить всё» не используется.
5. Валидация: атрибуты на DTO + повторная проверка в сервисе после `trim`:
   тема 5–80, описание 10–500, `roomId` — целое больше нуля. Короткий
   title → **400**, не 500.
6. Правила процесса в сервисе: статус должен быть из четырёх значений
   (иначе 400); перевод в `InProgress` без исполнителя → **409**;
   запись с несуществующим `id` → **404**; запрещённый переход → **409**.
7. Неожиданный сбой: `GlobalExceptionHandler` пишет в лог одну понятную
   строку (путь + тип ошибки) и возвращает клиенту безопасный
   `ProblemDetails` 500 «Не удалось обработать запрос» — без stack trace,
   путей и тела запроса.
8. Коллекция запросов экспортирована в `/docs/api-collection/tickets.postman_collection.json`
   (201, 400, 404, 409, 401/403 добавлены в ЛР11). README объясняет,
   как импортировать и какой базовый URL.

## 3. Обязательные проверки коллекции

| № | Запрос | Ожидание | Факт |
|---|--------|----------|------|
| 1 | Успешный `POST` | 201, в теле `id`, `number`, `status: "New"`, `assigneeUserId: null` | 201 |
| 2 | `POST` с title из 3 символов | 400 ProblemDetails | 400 |
| 3 | `GET /api/tickets/999999` | 404 «Обращение не найдено» | 404 |
| 4 | `PATCH …/status` без исполнителя | 409 «Нельзя перевести в работу без назначенного исполнителя» | 409 |
| 5 | Оба PATCH после назначения | 200 | 200 |

*Скрины ответов добавьте из своей коллекции при прогоне.*

## 4. Доказательство лога

Учебное исключение вызывали в сервисе после успешной валидации, сняли
скрин строки лога и убрали бросок перед коммитом:

```text
fail: backend.GlobalExceptionHandler[0]
      Unhandled exception; path=/api/tickets; error=InvalidOperationException
```

Клиент при этом получил `{ "status": 500, "title": "Не удалось обработать запрос" }`
без стека.

*(место для скрина строки лога из консоли `dotnet run`)*
